## 一、项目背景与问题

### 1.1 学生办事的真实困境

学校已经有统一的服务入口聚合页（校务服务网），共列出 **114 项**服务。表面上"什么都能找到"，
但实际使用中，学生遇到的不是"找不到入口"，而是：

- 知道叫什么，点进去发现**进不去**（要登录、只能在钉钉/微信里开）
- 入口分属不同系统，**同一件事有多个相似入口**（如"我要修 / 智能报修 / 智慧报修 / 网络报修"）
- 找到入口也不清楚**要准备什么、要跑几趟、多久办完**
- 办事结果**没有人替你记着**，错过截止时间只能自己承担

### 1.2 实测数据（本项目的核心论据）

对校务服务网 114 项服务逐一提取真实跳转地址并测试：

| 分类 | 数量 | 实测情况 |
|---|---|---|
| 钉钉专属深链 | 18 | 浏览器点击无反应，只能在钉钉内打开 |
| 由第三方（杭电助手）提供 | 19 | 页面正常，但并非学校自有系统 |
| 第三方后勤/图书馆页面 | 约 30 | 需支付宝/微信容器，浏览器体验差 |
| 学校自有系统 | 其余 | 全部需要统一身份认证 |

**结论：114 个入口里，能在浏览器打开即用的几乎没有。**

我们的知识库进一步验证了这个结论：收录的 31 件事中，

- 能在浏览器直接走完的：**11 件**
- 需要统一身份认证登录的：**13 件**
- 只能在微信 / 杭电钉里用的：**7 件**

典型例子：
- 场馆速约（`sportmeta.hdu.edu.cn/book/dingtalk/`）的 H5 登录入口 `/gymbook/authcertify/login?env=h5` 实测返回 **502 Bad Gateway**
- 第二课堂（`erke.hdu.edu.cn/weixin/`）走微信静默授权，外部浏览器无法登录

### 1.3 目标用户与场景

- 主要用户：大一至大四在校学生，尤其是刚入学、对办事路径完全陌生的新生
- 典型场景：要办一件事，但不知道该去哪个系统、要不要登录、是不是得在手机上开

## 二、解决方案

### 2.1 产品定位

> 一个**校园事务路由层**：用户说出要办的事，返回一张可执行的行动卡——
> 去哪办、在哪能打开、带什么、多久办完、依据是什么。

不替代任何现有系统，不代登录、不代提交，只解决"从需求到入口"这一段。

### 2.2 核心功能

| 功能 | 说明 |
|---|---|
| 自然语言问事 | "寝室没水了怎么办""体育馆怎么约" |
| 行动卡 | 入口 / 打开方式 / 步骤 / 材料 / 时限 / 依据 |
| **入口可用性标注** | 直接可用 / 需登录 / 需微信 / 需钉钉，并区分学校系统与第三方 |
| 入口总览页 | 31 件事按打开方式分组，直观呈现"入口分散" |
| 参数化深链 | 说"我想借《平凡的世界》"直接生成已填书名的馆藏检索结果 |
| 我的待办 | 行动卡一键加入待办，带截止倒计时 |
| 草稿预填 | 帮用户写好报修/申请文本，复制后自行提交 |

### 2.3 与现有产品的差异

| 维度 | 杭电助手 AI 助手（`ai.hduhelp.com`） | 本项目 |
|---|---|---|
| 技术形态 | FastGPT 文档检索问答 | 结构化知识库 + 规则/模型双通道检索 |
| 实时查询 | 答"无法确认……参考链接：暂无" | 图书馆可直接生成检索深链 |
| 入口可用性 | 不涉及 | 明确标注在哪能打开 |
| 持久状态 | 无 | 待办 + 截止倒计时 |
| 输出形态 | 一段文字 | 可勾选、可复制的结构化卡片 |

> 说明：上述对比基于 2026-11-10 对两个系统同一问题的实测记录，详见 `docs/ai-log/AI-LOG.md`。

## 三、技术实现路径

### 3.1 架构

```
用户输入
   │
   ├─ 有 LLM Key → /api/ask → 模型在知识库 id 白名单内选择 → 结构化卡片
   │
   └─ 无 Key / 超时 / 报错 → 本地关键词检索（触发词 + 二元组打分）→ 结构化卡片
```

前端只负责渲染结构化 JSON，**不直接接触任何模型密钥**。

### 3.2 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Vite + React 19 + TypeScript + Tailwind 4 | 构建快，产物小（约 83 KB gzip） |
| 形态 | 移动优先 PWA | 可添加到主屏幕，观感接近小程序，无需审核 |
| 后端 | 单个 Serverless 函数 | 唯一硬需求是保管 API Key |
| 持久化 | localStorage | 原型阶段无需数据库 |
| 知识库 | TypeScript 数据文件 | 换学校只换数据，代码零改动 |

### 3.3 知识库设计

每条条目包含：`id / category / triggers / title / summary / entry / steps / materials / sla / source / verified`

其中两个关键字段：

- `entry.access`：`none | login | dingtalk | wechat | alipay | mobile` —— 决定卡片如何提示
- `verified`：是否已与官方核对，未核实的条目标注「待核验」

字段规范见 `docs/KNOWLEDGE-SCHEMA.md`，条目来源见 `docs/CHORES.md`。

## 五、创新点与价值

1. **把"入口能不能用"变成一等公民**：现有导航产品只解决"入口在哪"，本项目额外回答"在哪能打开"。
2. **行动卡而非搜索结果**：输出是可执行对象（步骤 / 材料 / 时限 / 依据），可以照着做完。
3. **每条结论可追溯**：卡片固定展示依据，未核实条目显式标注，不编造链接与电话。
4. **两级降级**：模型不可用时退回本地检索，断网仍可演示，答辩现场不依赖网络。
5. **可迁移**：领域特定、架构通用，换学校只替换数据层。

## 六、总结与展望

（待写：项目收获、局限、后续方向）

已知局限：
- 知识库条目仍需逐条与官方核对
- 部分入口只能给出路径，无法一键直达
- 未接入任何需要登录的系统，因此无法查询个人真实进度

后续方向：
- 浏览器扩展作为数据采集通道（凭据不出本机）
- 多校配置包与条目共建
- 到期提醒（邮件 / 微信）
